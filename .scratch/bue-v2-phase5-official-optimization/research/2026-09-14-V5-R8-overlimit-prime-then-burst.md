## 1. 三分支对照 R7（本票要判的增量）

R7 §5.2 / §5.5 近似准入：**仅当**激活时主机 `ammo >= ammoPerShot` **且** 后备 `cap > 0`；空匣拒绝；`cap=0` 拒绝。空匣连发仍要伪造 `tockShoot` 的 `ammo`，与 R6 同因，不能安全。

本票想用「先压满再开窗」把空匣变成 R7 的有弹前提：

| 分支 | 产品 | 相对 R7 的增量 |
|---|---|---|
| 1 | 当前匣 `amount == 0` 且后备够填到 `MaxAmount` → 先现网式压弹（先箱后备用匣）**填满枪上匣** → 再进冻匣窗 | 若压弹真能把枪上匣写成满，则开窗时变成 R7 有弹近似；否则仍是空匣 |
| 2 | 当前匣 `amount > 0` → 不先压，直接进同一窗口 | 与 R7 近似同形；票面**没写**要求 `cap > 0` |
| 3 | 当前匣空且后备不够满匣 → 不激活，提示无后备 | 与 R7/T7「无匹配资源不激活」同形，无新射击问题 |

本票增量几乎全在分支 1 是否能用**现网** `TryRepackTransactional` 把枪上那一本写成满。下面五问按此展开。

## 2. Q1 — 现网压弹能否只填枪上那一本？

**结论：不能。现网只会填背包页 2..6 里的未满匣；不管枪上匣、不管 `UseableGun.ammo`、不管 `state[10]`。分支 1 若字面复用现网压弹，直接失败。**

### 2.1 扫描范围把装备槽排除在外

`TryRepackTransactional` 两处快照都是 `CapturePages(inv, PlayerInventory.SLOTS, PlayerInventory.PANTS)`（LIR-SVC `:108-109,118-119`）。`BuildRepackPlan` 扫描循环同样是 `for (byte page = PlayerInventory.SLOTS; page <= PlayerInventory.PANTS; page++)`（`:188`）。

原版页码（U3-PINV `:64-79`）：

| 页 | 常量 | 内容 |
|---|---|---|
| 0 | Primary | 主手装备枪 |
| 1 | Secondary | 副手装备枪 |
| 2 | `SLOTS` | 手持/Hands |
| 3..6 | BACKPACK..PANTS | 背包五页 |
| 7..8 | STORAGE / AREA | 储物箱/区域（本扫描也不进） |

文件头铁规 2 写死：「仅处理背包内容（page 2..6 = SLOTS..PANTS），跳过装备槽/储物箱/区域」（LIR-SVC `:21`）。页 0/1 的枪物品从未进入 `unfilledMags`。

### 2.2 枪上匣本来就不在背包 jar 上

即使扫描误进页 0/1，目标也找错字段。开火权威三套数字（R6 §2.1，此处不重抄路径）：

- 连发许可 = `UseableGun.ammo`（装备时从 `state[10]` 拷入，U3-GUN `:3513`）。
- 持久账本 = `player.equipment.state[10]`（`GunStateIndices.AMMO`，U3-IDX `:33`）。`fire()` 写它（U3-GUN `:886-893`），`updateState()` 把它写回**枪物品** `item.state`，不是枪物品 `item.amount`（U3-EQ `:1874-1885`）。
- 装备槽 `jar.item.amount` = **那把枪自己的堆叠数**。开火不碰；换匣读的是**新匣** `jar.item.amount` 再写入 `ammo`/`state[10]`（U3-GUN `:2908-2911`）。

枪上那本匣的发数活在枪 `state[10]` / RAM `ammo`，不是一件可被 `sendUpdateAmount` 改的背包 `ItemMagazineAsset` jar。现网 `BuildRepackPlan` 只把 `asset is ItemMagazineAsset` 且 `jar.item.amount < MaxAmountAsByte` 的背包槽当目标（LIR-SVC `:215-233`）。枪物品的 asset 是 `ItemGunAsset`，走 `else` 分支当「潜在弹药源」——且因页码已被排除，连这个误分类也不会发生。

### 2.3 弹药源同样只有页 2..6 的非匣物品

`else` 分支把非 `ItemMagazineAsset`、`amount > 0` 的物品收进 `ammoBoxMap`（`:235-256`）。**同类匣不当弹药源**：匣只当目标，不当箱。R7 要把备用匣当冻匣窗付款源是新规则；现网 B 没有「先箱后备用匣填某一本」的源优先级，更没有「只填枪上那一本」。

`CommitRepack` 只对计划里的 `(page,x,y)` 调 `inv.sendUpdateAmount` / `items.removeItem`（`:488-521`）。`sendUpdateAmount` 写的是该槽 `jar.item.amount`（U3-PINV `:1335-1344` → U3-ITEMS `:48-59`）。没有 `equipment.state[10]=…`，没有 `UseableGun.ammo=…`，没有 `sendUpdateState`。

权威层 `LirProductionAuthority.ExecuteRepack` 在准入后只调 `TryRepackTransactional`，按 outcome 映射返回（LIR-AUTH `:38-52`）。成功路径也不补枪状态。现网 Harmony 只有 `ReceiveAttachMagazine` 与 `forceAddItem`（LIR-MOD `:368-369`），压弹成功不会间接触发换匣。

### 2.4 压弹成功后枪上匣仍是空的

因此一次「现网式压弹」Committed 的真实效果是：页 2..6 若干未满备用匣 `jar.item.amount` 上升，匹配弹药箱下降或删零。owner/host 的 `UseableGun.ammo` 与 `state[10]` **保持激活前**（空匣仍是 0）。`tockShoot` 门槛仍是 `ammo >= ammoPerShot`（U3-GUN `:4513-4520`）。空匣继续停火。

### 2.5 分支 1 在现网压弹上是否直接失败？

**是，字面复用现网 B 则分支 1 直接失败**：空匣不会变成满匣；后续冻匣窗仍面对 R7 判定不可安全的空匣连发。压弹甚至可能把后备箱/备用匣填进**别的**未满背包匣，把本该留给枪上匣的弹药先花掉，再让开窗扫描发现后备不够——比「没压」更糟。

若另写「只填枪上匣」的新事务（改 `state[10]` + 同步 `ammo` + `sendUpdateState`，并从箱/备用匣扣满容差额），那就**不是现网压弹**，而是激活时一次把后备合并进当前匣。T7 Q5 明确禁止「把箱和匣合并进当前匣」；R6 §5.3 / R7 §5.4 对照表把「激活合并进当前匣」标成语义违规。本票问的是「先跑现网式压弹填满枪上匣」——现网做不到；做成新合并则产品违规。没有第三条现成缝。

## 3. Q2 — 填满成功后 `ammo` / `state[10]` 是否已经 `>= ammoPerShot`？

**对照现网压弹：否。压弹成功不改这两份，空匣仍 `< ammoPerShot`，不满足 R7「有弹才激活冻匣」。**

R7 §5.2 准入：激活时主机 `ammo >= ammoPerShot` 且 `cap > 0`。`ammoPerShot` 默认 1（U3-GAS `:136`）。`tockShoot` 只读 RAM `ammo`（U3-GUN `:4513`）。

现网 Committed 之后：

| 字段 | 压弹前空匣 | 压弹后（现网 B） |
|---|---|---|
| 页 2..6 未满备用匣 `jar.item.amount` | 可能上升 | 可能已满（若有兼容箱） |
| 弹药箱 `jar.item.amount` | 被扣 | 被扣 |
| `UseableGun.ammo` | 0 | **仍 0** |
| `equipment.state[10]` | 0 | **仍 0** |
| 装备槽枪 `jar.item.amount` | 与匣无关 | 不变 |

因此「填满成功」在现网语义里指的是**背包未满匣**填满，不是枪上匣。R7 冻匣前提读的是枪上 `ammo`。两套账对不上。空匣双击 R 即使压弹 Committed，下一拍 `tockShoot` 仍走 `:4522-4530` 停火，本地还会弹 RELOAD（`:902-905`）。

**反事实（不是现网、且 T7 禁止）**：若新代码把枪 `state[10]` 写成 `MaxAmount` 并同步 owner+host `ammo`，则 `ammo >= ammoPerShot` 成立，R7 有弹前提被满足。那是「激活合并」，不是本票的现网压弹。即便做了，窗口内仍要 R7 那套 `fire` 不写 `state[10]` / host 计发 / 出口 settle；且激活时已经把满匣子弹从后备扣进当前匣——与窗口结束再按开火发数扣后备是两笔账（见 Q3）。

HUD 分子读的也是 `ammo`（U3-GUN `:5347`）。现网压弹后空匣 HUD 仍是 0 / MaxAmount，不会出现「已填满再冻」的观感。

## 4. Q3 — 两笔账会不会打结？是否必须快照「压弹后剩余后备」作窗口上限？

**会打结。现网路径上第一笔已经可能扣了箱（却没填枪上匣）；第二笔再按开火发数扣箱会把同一批后备付两次，或第一笔把后备花光导致第二笔亏空。即便另写「只填枪上匣」，激活时已扣满容差额，窗口结束若再按 `shotsFired` 全额扣后备，满匣那笔被付两次。必须把窗口 cap 钉在压弹后的剩余后备；且第一笔若已把弹写进当前匣，结算不得再为「匣内已有的那些发」付款。**

### 4.1 现网压弹（分支 1 字面）——账在错误物品上打结

时间线：

1. 激活前：枪上 `ammo=0`；页 2..6 有箱 + 可能有未满备用匣。
2. `TryRepackTransactional`：箱 → **背包未满匣**（LIR-SVC `:274-351,493`）。枪上仍 0。
3. 若仍强行开 R7 窗：R7 要求 cap = 激活时主机扫描的后备可覆盖发数（R7 §3.1）。若 cap 用**压弹前**扫描，结束时箱可能已被第一笔扣光 → 亏空冷却，但窗内若用伪造 `ammo` 出了伤 = 整窗免费伤（R7 §4.6）。若 cap 用**压弹后**剩余，枪上仍空，窗仍要伪造许可才能打——回到 R7 空匣不可安全。

所以现网路径上「必须快照压弹后剩余」救不了分支 1：第一笔没把弹送进射击账本，第二笔无论用哪次快照都对不上「填满枪上匣再冻」。更糟的是第一笔可能先喂饱无关备用匣。

现网 B 与冻匣结算还会抢同一条权威缝：LIR-AUTH 闸约 1.5s（R7 §4.4）。窗口结束 settle 若被闸挡住后忘记补结 = 漏付款。R7 已要求会话与功能 B 互斥；本票再在激活时先跑一趟 B，等于同一双击要串两笔事务，闸/指纹/半提交（RestoreFailed 隔离）叠一层。

### 4.2 反事实：真的把枪上匣填满再开窗

假设新事务把当前匣从 0 补到 `MaxAmount`，从箱再备用匣扣了 `need = MaxAmount`（空匣差额）。枪上现在有 `MaxAmount` 发，已经付过钱。

冻匣窗产品是：期间不减当前匣，结束按窗口内打出的发数从箱+备用匣折算。若结算 `pay = shotsFired` 再扣后备：

- 玩家在窗内打了 `k` 发，当前匣账本仍是满的（不减）。
- 后备又被扣 `k`。
- 窗结束后玩家手里是满匣 + 已打 `k` 发的伤害。满匣那 `MaxAmount` 是第一笔付的；`k` 是第二笔付的。伤害只对应 `k`，但库存少了 `MaxAmount + k`。玩家被多扣一整匣。
- 若 `k > 压弹后剩余`，第二笔亏空，第一笔那匣还在枪上 → 白嫖满匣，第二笔惩罚冷却不能把匣清掉，除非 settle 再改当前匣（与「结束把当前匣恢复成激活前」相反：激活前是 0，恢复成 0 等于把刚压上的匣倒空，第一笔白做）。

因此两笔账的正确切分只能是下面之一，不能两笔都按「全额后备」算：

| 切分 | 第一笔 | 窗口 cap | 结束付款 | 当前匣 |
|---|---|---|---|---|
| A. 压弹即供弹，不再冻 | 填满并扣后备 | 不开窗 | 无第二笔 | 原版扣匣 |
| B. 冻匣，压弹只是抬许可 | 填满并扣 `need` | `剩余后备`（压弹后快照） | `min(shotsFired, 压弹后剩余)`；**不再**为匣内已有发数扣 | 窗内不减；结束保持满匣则匣内那些发已在第一笔付清，窗内打出的从剩余后备付 |
| C. 压弹当作垫款，结束倒回空匣 | 填满 | 压弹后剩余或压弹前总和 | 按 `shotsFired` 扣；再把当前匣恢复成 0 | 等于激活合并 + 结束掏空，T7 禁止合并，且倒空像删弹 |

切分 B 才接近票面「先压满再冻」。它**必须**：

1. 窗口 cap = **压弹提交成功之后**的主机后备总和，不是压弹前。压弹前快照会把已扣进当前匣的 `need` 重复算进 cap。
2. 结算源清单也必须是压弹后指纹；压弹改过的箱槽不能再用压弹前 preimage。
3. `pay = min(shotsFired, 压弹后剩余)`，不要 `pay = shotsFired + need`。
4. 当前匣若窗内未写 `state[10]`，结束无需恢复；若产品还要求「恢复成激活前 0」，则第一笔满匣被撤销，许可前提消失，且已出伤的 `k` 只能从后备扣——那是 R7 空匣问题换皮。

票面问「是否必须在激活时快照压弹后剩余后备作为窗口上限」：**是（对任何真把弹写进当前匣的实现）**。现网压弹写不进当前匣，这条快照解决不了分支 1。

### 4.3 分支 2 没有第一笔，但仍要激活瞬间快照

分支 2 不先压，只有 R7 那一笔。cap 仍必须是激活时主机后备（R7 §3.1），不是结算时扫描。与本票「压弹后快照」不是同一事件，但同构：上限钉在开窗瞬间，不是结束瞬间。

## 5. Q4 — 分支 2 后备为 0：结束不扣、只默认冷却，是否还触发 R7 漏结算免费伤？

**会。有弹 + 零后备开窗 = 窗口内冻匣等于没为伤害付钱（当前匣本就不减）。这不是「漏结算」的实现事故，是产品把 cap 设成 0 后仍然出伤。必须禁止「有弹+零后备」开窗，不能靠默认冷却买单。**

### 5.1 R7 已经拒绝 cap=0

R7 §5.2 准入第 1 条：仅当 `ammo >= ammoPerShot` **且** `cap > 0`。§5.5 安全步骤第 1 条：主机算 cap，拒绝 cap=0 与空匣。票面分支 2 写「当前匣 `amount > 0` → 不先压，直接进同一窗口」，**没有**复述 cap>0。若实施按票面字面放行零后备，就是关掉 R7 这条门。

### 5.2 为什么结束不扣 + 默认冷却仍是免费伤

冻匣窗的射击效果（R7 §3.2）：窗口内 `fire()` 跳过 `ammo -=` 与 `state[10]` 写入。当前匣数字冻结。伤害在每发 `fire()` 时已经生效（R7 §1 表：结束折算失败 = 已出伤未付款；§4.6 漏结算 = 整窗免费伤）。

零后备时：

- cap = 0。R7 近似本应根本不开窗。
- 若仍开窗且「结束不扣、只默认冷却」：`shotsFired` 无论多少，结算源是空的，`pay = 0`。当前匣不减。玩家打出的每一发都没有对应的箱/备用匣扣减，也没有当前匣扣减。
- 默认技能冷却只挡下一次双击，不撤销伤害，也不补扣弹（R7 §4.6：「惩罚冷却不能代替扣弹」；默认冷却更不能）。
- 这比「漏结算」更干净地免费：不是出口忘了 settle，而是 settle 故意不付款。权威层看起来「成功结束」，审计看不到 RestoreFailed。

对照「漏结算」：R7 漏的是有 cap、有 `shotsFired`、出口没跑扣库存。零后备开窗是 cap 一开始就是 0，结算即使跑了也是 no-op。玩家观感相同：窗内无限（直到最长持续）打当前匣里那点数字对应不到的伤害。

有弹本身不能当付款：产品写明「期间不减当前匣」「当前装上的匣不当源」（T7 Q5；R7 产品语义）。窗内消耗的必须是后备。后备为 0 则没有任何合法付款源。

### 5.3 产品可接受还是必须禁止？

**必须禁止「有弹+零后备」开窗。** 不是体验取舍。允许它等于官方技能提供限时 `infiniteAmmo`（`tockShoot` 仍要非空 `ammo`，所以只对有弹枪），冷却只是节奏税。T7/R7 的超限定义是「先消耗匹配弹药箱，再消耗备用匣余弹」的临时供弹；无匹配资源应不激活（T7 Q5：「无匹配资源：不激活，明确没有可用的匹配弹药」）。分支 3 已经对空匣+不够满匣写了「不激活」。分支 2 零后备是同一条「无后备」门，不能因为匣里还有几发就绕开。

可做的产品出口（都不开冻匣窗）：

- 与分支 3 同一提示「无后备弹药」/「没有可用的匹配弹药」。
- 有弹+零后备时退回一级/现网双击压弹：但现网 B 也填不满枪上匣，只会填背包未满匣；枪上有弹时玩家可能只想开超限。退回压弹不是超限。
- 有弹+零后备时什么都不做（原版单击 R 仍可用）。

「开窗、结束不扣、默认冷却」不在可做集合里。

### 5.4 与分支 1 的交叉

若有人用「先压再开窗」绕过空匣，又在压弹后后备为 0（刚好只够填满枪上匣、或现网把箱全填进了别的匣）仍开窗：这是 Q4 同一洞——cap=0 的冻匣。切分 B（§4.2）在压弹后剩余为 0 时应拒绝开窗，只留下已经付过钱的满匣走原版扣弹。那是普通压弹（且现网还压不到枪上），不是超限。

## 6. Q5 — 结论

三选一：**与 R7 同级缺陷不可做**（same-as-R7-unsafe）。不是「可安全做」。也不是「仅当禁止某分支就可安全做」——禁止分支 1 只是退回 R7 已给出的有缺陷近似，R7 已声明那不是安全闭环。

### 6.1 为什么不是「可安全做」

票面三分支要同时成立：

1. 空匣且后备够满匣 → 现网式压弹填满**枪上匣** → 再冻匣窗；
2. 有弹 → 直接开同一窗（票面未写 cap>0）；
3. 空匣且不够满 → 不激活。

(1) 被现网压弹打穿：`BuildRepackPlan` 只扫页 2..6，只改背包未满匣 `jar.item.amount`，从不写 `ammo` / `state[10]`（LIR-SVC `:188-256,493`；LIR-AUTH `:38`）。压弹后仍是空匣，`tockShoot` 不停伪造就不能连发——与 R7 §5.1 / R6 同一根绳子。

把 (1) 改成新事务填枪上匣 = 激活时把后备合并进当前匣。T7 Q5 禁止；R6/R7 对照表标语义违规。即便违规合并成功，窗口仍要 R7 全套 host+owner `fire`/`tockShoot` 补丁、出口 settle、拒换匣；再叠加 Q3 两笔账。现网没有这些补丁（LIR-MOD `:368-369`）。

(2) 若放行零后备，比 R7 更差：冻匣 + 无付款源 = 限时免费伤，默认冷却不能补弹（§5）。

任一支按票面做，第五阶段都不能把「先压满再冻」称为安全官方优化。

### 6.2 为什么不是「仅当禁止某分支时才可做」

禁止分支 1（永不对空匣开窗、也不做填枪上匣）+ 禁止分支 2 的 cap=0：剩下的正是 R7 §5.2 近似——有弹且后备>0 才激活，窗内不减匣，结束一次扣箱。那是 **R7 的产品**，不是本票新能力。R7 对它的判决是「只能做有缺陷的近似」，安全六步缺一则与 R6 一样不能做（R7 §5.5）。本票禁止分支并不能把那六步变成现成缝，也不能把空匣变成可打。

禁止分支 2、只留分支 1：更糟。分支 1 现网失败；新填枪上匣违规且两笔账打结。

禁止分支 3 无意义：分支 3 已是不激活。

因此「丢掉某个分支就安全」不成立。可丢掉的只是回到 R7，R7 已不是「可安全做」。

### 6.3 为什么是「与 R7 同级缺陷不可做」

| 面 | R7 | 本票三分支 |
|---|---|---|
| 空匣连发 | 须伪造 `ammo`，不可安全 | 分支 1 想用现网压弹绕开；现网不填枪上匣，仍须伪造 |
| 有弹冻匣 | 有缺陷近似（新 `fire` 补丁、漏 settle=整窗免费伤） | 分支 2 同构；票面还少了 cap>0 门 |
| 逐发改背包 | 已绕开 | 激活多一笔压弹，结束再一笔，账会打结 |
| 现网 LIR | 无开火补丁 | 压弹事务明确跳过装备槽 |

分支 1 没有剪断 R7 的许可绳子，只是在绳子前面加了一笔填错对象的库存事务。空匣路径与 R7 同级不可做；有弹路径不比 R7 更安全。第五阶段不要实施「空匣先压满再冻匣」。若仍要可玩切片，沿用 R7：空匣拒绝、有弹且 cap>0、文案不得叫空匣超限——那是 R7 的事，本票不升级它的安全等级。

### 6.4 对照表

| 方案 | 填枪上匣 | 空匣连发 | 冻匣不减 | 结束扣后备 | 第五阶段 |
|---|---|---|---|---|---|
| 票面分支 1 + 现网 B | 否（只填页 2..6） | 仍须伪造 | 叠 R7 | 两笔易双扣 | **不可做** |
| 分支 1 + 新写枪 `state[10]` | 是（合并） | 有弹后不须伪造 | 叠 R7 | 须压弹后 cap | 语义违规 + R7 缺陷 |
| 票面分支 2 含零后备 | 不压 | 否 | 是 | 不扣 | **免费伤，必须禁** |
| 分支 2 且 cap>0（=R7 近似） | 不压 | 否 | 是 | 一笔 | R7：有缺陷近似，非本票新安全 |
| 分支 3 不激活 | — | — | — | — | 可（已是拒绝） |
| R6 逐发供弹 | — | 须伪造 | — | 每发 | 已否决 |
| 降级：只跑现网 B | 否 | 否 | 否 | 压弹时扣箱填背包匣 | 可做，无超限射击 |

### 6.5 若有人把分支 1 误标成「压弹成功就能开窗」

清单（缺一则空匣窗或不付款）：

1. 现网 `TryRepackTransactional` **不会**让 `ammo`/`state[10]` ≥ `ammoPerShot`。不得把 Committed 当 R7 准入。
2. 不得用压弹前后备当 cap（第一笔已扣箱）。
3. 不得在 cap=0 时开冻匣窗（有弹也不行）。
4. 不得把填枪上匣写成现网 B 的一次调用。
5. 漏 settle 仍 = 整窗免费伤（R7 §4.6）。

## 8. 一句话

现网压弹只填背包页 2..6 未满匣，不填枪上匣、不改 `ammo`/`state[10]`；空匣先压再冻在现网路径上直接失败。真填枪上匣是 T7 禁止的合并，且与结束扣箱打成两笔账。有弹+零后备开窗是冻匣免费伤，必须禁止。三分支产品与 R7 同级缺陷不可做；禁止分支 1 只是回到 R7 近似，不是本票可安全做。

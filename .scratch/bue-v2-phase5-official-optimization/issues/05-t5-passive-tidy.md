## Question

用户原话：重新启用被动整理——例如两格物品面对两个离散一格空位时，应当可以拾取并触发一次整理。这不是新功能：原 LaunchInventoryTidy v1.4.0 以 Harmony 拦截 `Items.tryAddItem`（`tryFindSpace` 失败则整页重排含新物品）；v1.4.1 用摘掉 `[HarmonyPatch]` 硬禁用（审计禁止 Prefix 内加开关，避免误触发面残留）；BUE DEV-V2-15 未移植该 patch，生产程序集断言其缺席。重新启用 = 恢复拦截，不是翻一个现存 bool。

本票裁决产品语义：

1. **触发条件**：仅当原版 `tryFindSpace` 失败（用户举的碎洞例子），还是每次成功放入也重排？失败后整理仍放不下是否回退为原版失败（物品留在地上）？
2. **作用页**：只玩家页 2..6，还是含 T4 批准的容器？原插件日志写过「仅支持玩家 page 2-6；容器整理未实现。被动整理保持禁用。」
3. **与「自动整理」词汇**：更好的物品交互明确禁止自动整理。被动整理是否必须保持独立术语，且默认不在拖放预览路径触发？
4. **玩家控制**：始终跟随背包整理功能启停，还是另设一条 ClientPreference（默认开/关）？原禁用原因若是误触发，本阶段用什么约束换回（仅碎洞失败、节流、可关）？
5. **权威与联机**：`tryAddItem` 在客户端与服务端谁跑？被动整理是否必须走与按钮整理同一套服务端权威，禁止只在本地改网格？
6. **与整理后自动压弹**：被动整理成功是否发 `TidyCompleted`，从而触发 LIR 现有「整理后自动压弹」？预期要显式裁断，避免拾取一件衣服就压弹。

禁止：做成更好的物品交互的一部分；用 Prefix 内死开关冒充禁用（沿用 v1.4.1 审计口径，要么登记 patch 要么类型缺席）；本票改求解器（排序归 T3）。R4 是事实输入。

## Answer

2026-09-14 用户把本票扩成**两条整理恢复路径**后定音。跨表面共享裁决：被动整理属背包整理、不挂拖放预览、不用 Prefix 内死开关。整理排序票：凡背包整理入口消费统一排版。容器整理票：本阶段容器按钮整理走会话，不对容器默认开被动整理——本票将「容器侧」收窄为 **Ctrl+右键快速转移失败后只整理接收侧目标网格**，不是开箱捡东西时的被动整理，也不替代容器标题栏按钮。

原版事实（必须写进实施规格，避免抄错缝）：

- 拾取 / 合成入包：主机 `tryAddItem` / `tryAddItemAuto`。旧 Prefix 只看得见这条。
- Ctrl+右键在玩家库存 ↔ 已打开容器之间：客户端 `onSelectedItem` 在 `ControlsSettings.other`（默认左 Ctrl）且 `isStoring` 时本地 `tryFindSpace`，成功才 `sendDragItem` → 主机 `ReceiveDragItem`（`ONLY_FROM_OWNER`）做 `removeItem` + `addItem`。**不调用** `tryAddItem`。碎洞导致客户端找不到矩形空位时**根本不发包**。更好的物品交互不拦截 `onSelectedItem`。因此快速转移恢复**不能**靠恢复 `ItemsTryAddItemPatch`。
- Ctrl+右键从地面摊（AREA）进容器走 `takeItem`，那是拾取 RPC，归入包路径，不归快速转移恢复。
- 旧被动路径 TryPack 报成功但新物品未放入仍 `__result=true` = 吞物。本票禁止原样搬这条。

### Q1 — 只在原版第一次失败后恢复一次

两条路径：

1. **拾取 / 合成入包恢复**：主机原版入包失败（找不到合法空位）→ 整理玩家库存一次（含待加入物品）→ 再试放入。第一次成功不整理。
2. **Ctrl+右键快速转移恢复**：原版快速转移因目标网格碎洞失败（含客户端因 `tryFindSpace` 失败而未发包）→ 只整理**接收侧目标网格**一次 → 再试同一件转移。第一次成功不整理。

恢复成功必须同时：待加入/待转移物品在计划中；不重叠、不越界、集合一致；相关版本仍有效；主机提交成功。任一失败 → 原版失败语义 + 零修改。拾取/合成：物品留原处、未入包。快速转移：源和目标都保持原状。禁止报成功却删物；禁止转移失败但目标已被单独整理。

### Q2 — 范围

入包恢复：只玩家五页（手、包、甲、衣、裤），把现有物品 + 待加入物品一起交给统一排版。排除主副手槽、AREA、容器页、虚拟容器、未裁决页。第一版只接线主机权威拾取 / 合成；奖励或插件发放等其它获得路径必须另裁，不能因共用 `Items` 类型自动获得。

快速转移恢复：只整理接收侧。玩家→容器则整理当前打开且受支持的容器（世界容器 / 已授权后备箱；虚拟箱本阶段不支持）。容器→玩家则只整理原版选定的那一玩家页；若原版会按固定顺序试多页，恢复必须复现同一顺序，不得升格全身整理。源网格不整理。

两条路径都调用同一统一排版模块，不得复制分类/主体/行带/旋转。

### Q3 — 跟随背包整理生命周期，无独立开关

LIT Running → 登记两个恢复适配器。Stopped / Disabled / Isolated → 拆除或失效，完全回到原版。禁止 Prefix 内 `if (!enabled) return`。优先 Start 登记、Stop/Isolate 注销、再启用换代际重登记。若底层补丁无法物理卸载，停用态必须证明两条路径都不执行；这是兼容方案不是首选。

### Q4 — 主机权威；快速转移要自报失败

两条都在主机执行规划与提交。客户端不得自行重排或伪造成功。

入包恢复挂在主机入包判定失败之后。快速转移因客户端失败就不发包，实施必须增加「客户端发现目标碎洞」后向主机请求恢复的缝（绑定请求者、源物品、源/目标网格、容器会话、版本/指纹、数量与状态），由主机重验后规划目标网格并原子提交排版+转移。会话关闭、opener 变、离座、插件关箱、源物已走、版本过期、计划非法、提交失败 → 零修改。

不与更好的物品交互拖放预览混用。拖放松手仍禁止整页重排。

### Q5 — 不发整理完成、不自动压弹

两条恢复成功都不发布 `TidyCompleted`，不触发整理后自动压弹，不新增公开事件，不扩大 2.1。内部诊断（例如入包已恢复 / 快速转移经目标整理后完成）可以记，但不是功能事件。玩家意图是获得或移动那一件东西，内部排版不是点「整理」。

### 本票不做

新 FeatureId；每次成功放入/转移都整理；吞物；把恢复做成更好的物品交互；Prefix 内死开关；本票改排版算法；地面摊 Ctrl+右键进容器冒充快速转移（那是拾取）；其它未接线的获得物品路径自动享受入包恢复。

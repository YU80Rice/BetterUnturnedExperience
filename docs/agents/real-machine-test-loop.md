# 实机测试循环（Real-Machine Test Loop）——DEV-16D 起强制执行

> 来源：用户 2026-08-30 指令持久化。适用于 DEV-16D 及其后所有工单的"真机读数驱动修复"循环。
> 本文档是 `docs/agents/output-review-loop.md` 的实机测试轮补充细则，与其同效力。
> **自动化扩展（2026-09-07）**：U3DS 实机链（部署→启动→锚行→computer-use 干净退出→证据包）已由 Agent 全自动验证，SOP 见 `docs/agents/auto-rm-test-sop.md`——实施票交付候选后按该 SOP 自动采集证据包，停等用户人工验收；人工验收与关单仍归用户。

## 每轮实机测试的标准顺序（不可跳步、不可调换）

1. **用户实机测试**，提交 UMM 诊断包。
2. **分析日志**，定位问题所在（引用日志行，不猜测）。
3. **修复循环**（见下节），完成全部修复步骤。
4. **Standards/Spec 双轴独立审查**（并行子代理，互不可见）。
5. **审查未 CLEAN 前，不得通知用户实机测试**——无论判别实验价值多大。
6. **审查 CLEAN 后**，生成新交付物：
   - Release 构建 DLL（0 errors / 0 warnings）
   - SHA-256 记录（`audit/<date>/rN-dll-sha256.txt`）
   - 产物目录（`artifacts/<case>-rN-<date>/`）与 CandidateBuild 标注
   - CaseId（`<ticket>-rN-<date>`，仅 CLEAN 后授予）
   - 交付报告（本轮变更、验证矩阵、判读要点）
7. **明确告知用户**："现在可以开始实机复测"，并给出**准确 DLL 路径**与**部署步骤**（含 certutil 哈希核对）。

## 修复代码的标准流程（步骤 3 的展开）

1. **记录审查阻断**（审计文档/工单注释——阻断内容、发现来源、严重级别）。
2. **解冻代码**（冻结期仅只读审计）。
3. **修复真实 `itemsPanel/grid/scroll` 挂载与坐标问题**（不做表面修补——坐标系、层级链、生命周期是根因层）。
4. **重新写红测并确认失败**（红测必须先于修复运行并失败——不允许"写完修复再补测试"）。
5. **修复到绿**（红测转绿 + 不回归）。
6. **重新编译（0/0）、全套测试（7/7）、静态门禁（NoUiTokens 等全 PASS）**。
7. **重新进行 Standards/Spec 双轴独立审查**（并行子代理）。
8. **如果仍为 FAIL，继续循环**（回到步骤 1 记录新阻断）。
9. **直到 CLEAN 后才交付 DLL 给用户测试**。

## 历史违规记录（本会话，作为教训）

- R25/R28/R30/R33/R37 多轮以"判别实验优先"为由在复审未 CLEAN 时交付部署 DLL——**均违反本流程**。
- 后果：R30 判别版把两个 patch 的失败混在一个 catch 里丢目标名；R39 部署指令在复审返回前发出。
- 教训：**判别实验可以先做，但交付给用户的 DLL 必须是已审产物**。判别与审查并行动作时，部署指令必须等复审返回。

## 判别实验与交付的边界

- 判别实验（instrumentation build）**可以**在复审未 CLEAN 时构建，但**只能自用**（本地构建验证编译），**不得**写入 `artifacts/` 交付目录、**不得**给用户部署指令。
- 判别日志（如 `placement-decision`、`placement-passthrough reason=`）属于生产诊断仪器，其代码本身按正常红绿+审查流程交付。
